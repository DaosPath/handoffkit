# HandoffKit 1.70 — LTS Qualification

> Status: **planned**. Version 1.70 is a qualification target, not a promise that every earlier experimental capability becomes stable.

## Goal

Produce a long-term-support release from capabilities that have real implementations, integrated execution paths, interoperability evidence, operational qualification, and maintained ownership.

## Entry criteria

1. The 1.19.5 security baseline has an exercised upgrade path.
2. Browser, app, extension, native, edge, ML, and distributed products each carry an explicit support classification.
3. Stable products pass their complete runtime, platform, packaging, recovery, and security matrices.
4. Experimental and provider-dependent features remain labeled as such.
5. Planned or unavailable capabilities are absent from positive marketing and runtime advertisements.

## LTS deliverables

- frozen 1.x wire and compatibility contracts;
- supported-product and platform matrix;
- signed artifacts, SBOMs, provenance, checksums, and install verification;
- migration paths from 1.19.5 and supported intermediate releases;
- rollback and disaster-recovery runbooks;
- deprecation schedule and maintenance ownership;
- security response and dependency patch policy;
- reproducible benchmark baselines;
- conformance kit and certification evidence;
- documentation generated from the same capability ledger used by runtime reporting.

## Product decision table

For every package, app, service, extension class, backend, platform, and provider, the release review records:

| Field | Required answer |
| --- | --- |
| Declared | Is there a public contract or documented name? |
| Implemented | Is there a real backend and execution path? |
| Integrated | Is it connected to authentication, replay, authorization, dispatch, and lifecycle where applicable? |
| Interoperability tested | Which runtimes/providers executed it together? |
| Operationally qualified | Which packaging, recovery, load, and failure tests passed? |
| Classification | Stable, experimental, provider-dependent, planned, or unavailable |
| Owner | Who maintains and responds to failures? |

Any missing required answer blocks a `stable` classification.

## Release gates

- clean source tree and reproducible build inputs;
- all supported Python, JavaScript, Rust, Go, and C++ products built from the release commit;
- package metadata and embedded versions verified from built artifacts;
- cross-runtime and cross-version compatibility suite;
- upgrade, rollback, migration, and corruption suite;
- performance regression budgets for p50/p95/p99, throughput, and memory;
- security tests for TLS, identity binding, replay, authorization, signatures, revocation, and key handling;
- representative x64/ARM64, desktop/server/edge, and browser-engine qualification;
- no publish until every artifact gate has succeeded.

## Compatibility policy

Breaking wire formats, package identities, or stable public APIs do not enter 1.70. They require a separately planned 2.0 train with migration tooling and dual-version interoperability.

## Explicit non-goals

- stabilizing a feature solely to make the version list look complete;
- relabeling provider-dependent behavior as universally supported;
- releasing packages that were not built, inspected, and tested from the final commit;
- publishing, tagging, or promoting artifacts before the evidence ledger is closed.
