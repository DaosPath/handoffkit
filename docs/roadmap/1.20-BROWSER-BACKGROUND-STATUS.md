# HandoffKit 1.20 Browser background status

This report describes the work currently implemented on the development branch.
It is not a release announcement and does not mark Browser Real as available.

## Implemented and integrated

`web_deep_research` is now an agent-facing route in JavaScript, Python, and C++.
It runs search, URL ranking, bounded fetch/exploration, Markdown extraction,
citations, and structured steps through the selected `WebTransport` in the
current process. Its default route never launches a user browser window.

JavaScript and Python also expose an experimental/provider-dependent
`user_browser` search adapter. A host may inject a bridge with
`search(query, options)` for its already-authorized browser session. The bridge
is explicit, normalizes only HTTP(S) results, and never gives the library access
to cookies, profiles, credentials, or arbitrary browser control. C++ and the
standalone CLIs have no such bridge and report
`user_browser_bridge_required` when that provider is selected.

The route records:

- `mode: "deep_search_then_explore"`;
- `metadata.execution_mode: "background_http"` by default, or
  `"background_user_browser_bridge"` when `user_browser` is selected;
- `metadata.user_browser_required` and
  `metadata.user_browser_bridge_configured` make that dependency explicit;
- provider transport (`http` or `map`), query/page/depth/concurrency limits;
- candidate URLs, timings, citations, failed steps, and partial-result errors.
- requested/used providers, provider errors, and provider codes; the supported
  adapters are DuckDuckGo HTML and Wikipedia OpenSearch, the self-hosted
  SearXNG JSON provider (`searxng`, configured via `HANDOFFKIT_SEARXNG_URL`),
  plus the optional
  injected `user_browser` bridge in JavaScript/Python;
- stable `error_code` values for query/provider/no-result and bounded research
  failures while retaining human-readable `error` text;
- cache hits, misses, and writes when a `BrowserCache` is supplied.
- provider defaults propagate through JS/Python/C++ kit helpers and registered
  tools; the JS CLI exposes repeated `--provider` or comma-separated
  `--providers` flags without contaminating query text with option values.

The same behavior is exposed as:

- JS `gatherDeepWebResearch()` and `createBrowserAgentKit().deepGather()`;
- JS/Python `web_deep_research` ToolRegistry tools;
- Python `gather_deep_web_research()` and `create_browser_agent_kit()["deep_gather"]`;
- C++ `gather_deep_web_research()` and `web_deep_research`.

## Still unavailable or incomplete

- Browser Real / Chromium / Playwright control, DOM automation, or a bundled
  user-browser bridge;
- arbitrary page JavaScript, DOM automation, screenshots, downloads, and user profiles;
- local full-web index independent of public providers;
- complete Browser Core golden vectors and all planned Fusion/Mission Control/Recovery Lab gates;
- full remote HTTP/provider, packaging, ARM64, and cross-runtime release qualification.

Provider availability is runtime-derived. A provider name or fixture does not
claim live-web reachability; an empty, unsupported, missing-bridge, or failed
provider result remains a structured partial/error result. The route still
depends on public provider endpoints when HTTP transport is selected and is not
an independent web index. Selecting only `user_browser` never falls back to
DuckDuckGo implicitly.
