# HandoffKit 1.40-1.49 — Extension Ecosystem

> Status: **planned**. Names and manifests alone do not constitute extension support.

## Goal

Create a controlled ecosystem for reusable complements without mixing examples, providers, connectors, UI panels, and executable workers into one ambiguous package category.

## Extension categories

| Category | Purpose | Execution expectation |
| --- | --- | --- |
| Provider | Model or service backend | Capability-detected adapter |
| Browser adapter | Search, engine, index, or extraction backend | Browser policy boundary |
| Connector | External data source or destination | Credential-scoped, audited I/O |
| Tool | Narrow callable operation | Typed input/output and authorization |
| Worker | Long-running or compute operation | Isolated lifecycle, cancellation, deadlines |
| Storage adapter | Artifact, state, index, or key backend | Durability and consistency contract |
| UI panel | Studio surface | Sandboxed UI contract and accessibility |
| Recipe/template | Composition with no hidden privilege | Declarative or explicitly bounded code |
| Demo | Learning and validation artifact | Never a production dependency |

## Repository placement

Each language ecosystem receives an `extensions/` area for source owned by that runtime. Cross-runtime examples live under `demos/`, not inside libraries. Shared contracts and test vectors remain under `shared/`.

An extension promoted from a demo must gain:

- an owner and lifecycle policy;
- real integration tests;
- capability detection;
- secure defaults;
- packaging and upgrade coverage;
- documentation that distinguishes stable, experimental, provider-dependent, planned, and unavailable behavior.

## Trust model

- Bundle identity and integrity are verified before loading.
- The signer is allowlisted by local policy.
- Permissions are granted locally and can be narrower than requested.
- Executable code runs only in a supported isolation backend.
- Revocation and expiry are checked at install and activation time.
- Network, filesystem, secret, browser, and compute access remain separately authorized.

## Non-goals for this train

- automatic publication to a public marketplace;
- arbitrary in-process native code loading;
- approval bypass from a trusted-looking package name;
- treating a signature field as verified without cryptographic verification;
- one extension package that silently downloads different executable code at runtime.
